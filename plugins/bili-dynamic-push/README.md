# B站动态推送（bili-dynamic-push）

盯住指定的 B 站 UP 主：一有**新动态**、以及**开播 / 下播**，就自动发到指定的群/私聊。
**不经过模型、不花 token**，到点就跑（确定性型插件，放 `plugins/`）。

推送内容长这样：

```
【B站动态】明日方舟终末地 转发了动态（10-02 19:04）
<正文>
https://t.bilibili.com/1253695825563877448

【B站开播】明日方舟终末地 正在直播
《明日方舟：终末地》「丹青渡」版本前瞻特别节目
https://live.bilibili.com/1921300321

【B站下播】明日方舟终末地 的直播结束了
```

> 直播走的是**直播间状态接口**（和动态检查是两台不同服务器、互不影响），
> 靠 `live_status` 判定：`1`=直播中（开播提醒）、从在播变成不在播（下播提醒）。
> 「轮播」（重播录像）不算开播，不会打扰你。
> **开播与下播是两个独立开关**，可以只留一个；关掉下播时状态照样记录，
> 不会因此漏掉下一次开播提醒。
> 开播提醒的最长延迟 = 检查间隔（默认 10 分钟，所以很短的下播-开播可能被合并成一次）。

## 两种用法（挑一种就行）

### 用法 A：在群里说一句话（最省事）

在目标群里对机器人说：

> 订阅 伊莫可Imoko 的动态

机器人会立刻回一条确认 + TA 当前最新的一条动态，之后每 10 分钟检查一次，有新动态自动发到**这个群**。

- 取消：`取消订阅 伊莫可Imoko` 或 `别推伊莫可了`（说 `取消全部订阅` 清空本群）
- 查看：`订阅了哪些` / `都关注了谁`
- 排错：`动态推送什么状态`（会打印上次检查时间、结果、错误原因）

### 用法 B：在「插件」页的齿轮里填设置

| 设置项 | 填什么 |
|---|---|
| 要盯的 UP 主 | uid（数字，最准）或名字，如 `伊莫可Imoko` |
| 推送到哪些群/私聊 | 群号，如 `123456`；多个用逗号分隔；私聊写 `private:QQ号` |
| 检查间隔（分钟） | 默认 10，最小 5（查太勤会被 B 站限流） |
| 开播提醒 | 默认开。TA 开播时推一条（带直播间标题和链接） |
| 下播提醒 | 默认开。觉得啰嗦可以**单独关掉**，开播提醒不受影响 |
| 每次最多推几条 | 默认 3，防止积压时刷屏 |
| 首次先把最新一条推出来 | 默认开，用来确认推送链路是通的 |

群号在哪看：控制台左侧的会话/群列表里就写着 `group:123456`。

## 抓不到某个账号的动态？

B 站的「动态」接口对**官方号 / 企业号（机构认证）**的匿名请求会返回空列表
（实测：明日方舟终末地、原神 都是 `code:0` 但 0 条；而个人 UP 主如影视飓风正常返回 12 条）。
这不是本插件的 bug，是 B 站侧的可见性限制。解决办法：在设置里填 **B 站登录信息**。

**怎么拿到它（一次性的，30 秒）：**

1. 用浏览器打开并登录 <https://www.bilibili.com>；
2. 按 `F12` 打开开发者工具 → 切到 **Application**（中文版叫「应用」）标签；
3. 左侧 **Cookies** → `https://www.bilibili.com`；
4. 在列表里找到名为 **SESSDATA** 的那一行，双击它的 **Value** 列，整段复制；
5. 回到 QQ Agent「插件」页 → 本插件的齿轮 → 把这段值粘进 **B 站登录信息** → 保存。

填进去之后设置页只会显示 `******`，插件读到的才是明文；留空 = 完全匿名。

> ⚠️ SESSDATA 等于你的 B 站登录凭证，别发给任何人（包括别粘到群里）。
> 本插件只把它拼进对 `api.bilibili.com` 的请求头，不会写进日志、不会外传。

## 排错

| 现象 | 原因 / 办法 |
|---|---|
| 「插件」页显示"加载失败" | 把页面上的错误原文发给我；多半是 QQ Agent 升级后 `src/` 里的模块挪位置了 |
| 设置填完没动静 | 等 1 分钟（设置一改就会自动检查一次）；再看 `动态推送什么状态` |
| 报"B 站限流 / 风控" | 检查间隔调大一点（≥10 分钟），等几分钟再试 |
| 报"抓不到发送通道" | QQ Agent 的 SnowLuma（OneBot）没连上，机器人自己也发不了消息 |
| 想从头再来 | 删掉 `data/bili-dynamic-push-state.json`（记录着已推过的动态和订阅名单） |

## 实现上的取舍（给以后改代码的人）

- 发送**复用核心的发送管道**（`src/sender.js` 的 `SendQueue` + `src/onebot.js` 的
  `OneBotClient`），排队/限频/去重/切分/CQ 转义与机器人自己发言一致。
- **只借 HTTP 通道，绝不调 `onebot.connect()`** —— 再开一条 WebSocket 会让群消息事件收到两份。
- 发送**不写进聊天的 self 留档**（传的是空 store），避免与核心的 ChatStore 双写同一文件；
  代价是机器人下一轮不知道"这条是它自己发的"。
- 已推过的动态 id 记在 `data/bili-dynamic-push-state.json`；某次发送失败也照样记账，
  宁可偶发漏一条，也不要重推同一条。
- 只发文字 + 链接，不发图：B 站 CDN 的图在 QQ 端抓取经常失败，半成功比少一张图更糟。
