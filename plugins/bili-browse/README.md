# 自己刷B站（bili-browse）

让机器人在**没人说话的时候自己去刷 B站**：后台定时挑一个视频，把标题、简介、
播放数据、热门评论，以及**B站 自己抽好的逐帧画面**一起备好；等到它因为冷场被
主动唤醒时，就像随口聊天一样把链接分享到群里，说说自己的看法。

还支持（2026-10-14 新增）：

- **按播放量 / 点赞数 / 发布时间范围筛选**要挑什么样的视频
- **触发词主动发视频** —— 群里有人提到指定词就确定性地发一个
- **仅 @ 模式** —— 只有被 @ 到时才发
- **发完自动补一句锐评** —— 用自己的口气说一两句看法

配了 B站 登录态并显式打开后，还能在视频下**发一条真评论**，发完回群里说一声。

---

## 它解决什么问题

这类宿主是**事件驱动**的：只有"有人发消息"或"主动机会到了"，角色才会被唤醒。
冷场时的主动机会原本只能靠它硬聊，或者临时 `web_search` —— 慢、费 token，
搜到的还多半是标题党摘要。

本插件把那件事**提前做完**：后台定时挑一个视频、连画面一起备好（**完全不花 token**），
主动机会来临时直接递进提示词。于是它开口时是真"看过"东西的。

---

## 四条通路，别搞混

这个插件同时有**四条**各自独立的通路，配置项也分别对应。先看清哪条是哪条：

| 通路 | 触发条件 | 谁决定发不发 | 花 token |
|---|---|---|---|
| **① 冷场递料** | 主动机会（群里安静了） | **模型**（可能不发） | 是 |
| **② 触发词发送** | 群里出现 `triggerKeywords` | **插件**（确定性发） | 锐评那步会花 |
| **③ 仅 @ 发送** | 被 @ 到 | **插件**（确定性发） | 同上 |
| **④ 按需查看** | 模型调 `bili_watch` | **模型** | 是 |

①②的关系：① 是"备好了、你有机会就说"，② 是"有人点名，你必须发"。
**额度也是分开算的** —— 冷场分享用光了不会影响你叫它发（见下方配置表）。

## 筛选：播放量 / 点赞数 / 发布时间

| 设置 | 含义 |
|---|---|
| `minViewCount` / `maxViewCount` | 播放量区间（0 = 不限） |
| `minLikeCount` / `maxLikeCount` | 点赞数区间（0 = 不限） |
| `maxAgeDays` | 只看最近 N 天发布的（0 = 不限） |
| `minAgeDays` | 只看 N 天以前发布的（0 = 不限） |
| `filterFallback` | 筛空时自动放宽一次（默认开） |

### 三条实测得出的结论（都很反直觉，别改回去）

**① `0` 不是"未知"，是真的 0。**
搜索接口的 `play` / `like` 字段**总是存在**。一条刚发布、真的没人看的视频拿到的是
`0` 而不是 `undefined`。所以"没给这个字段就放行"的逻辑必须用
`Number.isFinite()` 判断，**不能**写成 `值 > 0` —— 后者会让 0 播放的视频静默
绕过"播放量下限"，用户设了"只要 1 万播放以上"却会收到 0 播放的刚投稿。
字段**真的缺失**（NaN）时才放行。

**② 绝不能把排序换成 `order=pubdate`。**
直觉是"按时间筛选就该按时间排序"，实测证明错得很彻底。B站的 `order=pubdate`
返回的是**刚刚发布**的那一批，播放量几乎全是 0。实测前 5 页 100 条，播放中位数
0~18、最高 18。于是"发布时间 + 播放量"一起用时候选全空：

```
条件：播放≥1万 且 点赞≥500 且 30天内（3 个关键词各跑一遍）
  默认相关度 + 30天窗 + 3页   → 存活 96 条   ← 最优
  默认相关度 + 30天窗 + 1页   → 存活 37 条
  默认相关度（无时间窗）+ 1页  → 存活 28 条
  order=pubdate + 30天窗 + 3页 → 存活  0 条   ← 全军覆没
```

正确做法：**时间窗交给服务端 `pubtime_begin_s/end_s`，排序保持相关度**。
时间窗只负责"限住时间"，相关度排序负责"把高播放的排前面"，两者叠加才成立。
所以 `searchVideos` **刻意不提供 `order` 参数** —— 留着它迟早有人重新踩进去。
（定标脚本：`bili-browse-tests/probe-ordering-sweep.mjs`，改之前先重跑一遍。）

**③ 翻页是筛选能不能用的关键。**
候选越多才越有得挑（1 页存活 37、3 页 96）。页数按 `perPage` 缩放
（`candidatePages()`）：perPage ≤20 时翻 3 页，≤35 时 2 页，再大就不翻 ——
用户把 perPage 调到 50 时本来就不缺候选，没必要多付请求和风控风险。
翻页中途某页失败**不影响**已拿到的候选；但**第 1 页**失败必须抛错，
否则会把"搜索被风控"伪装成"没有候选"。

### 筛空时会自动放宽一次

筛选条件之间可能互相冲突 —— 最典型的是 `maxAgeDays=1` + `minViewCount=10000`：
刚发的视频不可能有 1 万播放，这个组合在 B站 几乎无解。

硬扛的表现是"功能开着但一直没动静"，属于最难查的那类故障。所以默认
（`filterFallback=true`）会**自动放宽一次**，顺序是刻意的：

1. 先放宽**时间窗**（1 天 → 30 天 → 不限，并重新取候选）
2. 再放宽**播放/点赞下限**（砍半）

先动时间窗是因为它对用户意图伤害最小。反过来先放宽播放量就等于
"你要高播放的，我给你低播放的"，更偏离本意。

**每次放宽都会打日志写明放宽了什么** —— 静默放宽等于骗用户。

## 触发词 / 仅 @ / 锐评

| 设置 | 默认 | 说明 |
|---|---|---|
| `triggerKeywords` | 空 | 逗号分隔。留空 = 关掉触发词功能 |
| `triggerSendEnabled` | `true` | 触发词的开关 |
| `triggerCooldownMin` | `20` | 两次触发发送最小间隔（分钟） |
| `triggerMaxPerDay` | `10` | 每天最多被触发几次 |
| `atOnly` | `false` | **仅 @ 模式** |
| `autoReview` | `true` | 发完自动补一句锐评 |

### 为什么触发判定放在 `onMessage` 钩子

`onMessage` 是**确定性**的（每条消息必过），而 `before-llm-messages` 只在
真正要跑模型时才触发 —— 宿主按参与度档位判定"不响应"时根本到不了那里。
触发词若挂在后者上，就会出现"我说了那个词，但它那轮没被唤醒，于是永远不发"，
而这正是用户配触发词要避免的事。

### 为什么钩子里**不**直接发

钩子超时是 **5 秒**（`skills/manager.js` 的 `DEFAULT_HOOK_TIMEOUT_MS`），而
"现搜一个视频 + 拉详情 + 拉评论 + 拉拼图"要 3~8 秒，还会赶上 B站 风控。
在钩子里同步抓就等于一半概率被超时掐断 —— 表现是"有时发了、有时没反应"。

所以钩子只做**登记 + 起一个后台任务**（几微秒就返回，不挡住 ingest 热路径），
抓取与发送交给 `runTriggerSend`（fire-and-forget，自带并发保护与错误兜底）。

### 触发计数与分享计数是**两份**账

不共用一份计数是刻意的：分享额度是"别刷屏"的软约束，触发额度是"用户叫我发"的
硬承诺。共用会导致"冷场分享用光了额度，于是我 @ 它它也不发" —— 那是最不能
接受的失败。

另外触发发送**不看静默时段**：是人叫它发的，半夜叫也该发。静默时段只管 ①。

### 「仅 @」模式（`atOnly`）

打开后：

- 触发词必须**同时带 @** 才算数（@ 判定走宿主 `src/prompt.js` 的 `isAtMe`，
  QQ 号优先、名字兜底 —— 自己写名字匹配会在群名片与配置昵称不一致时叫不醒）
- **冷场递料通路整条关闭**（那个模式的语义就是"我不叫你你就别发视频"）

### 锐评

视频发出去之后，用**主模型**再调一次，让它用自己的口气补一两句看法。

- 发送是插件**确定性**完成的（不经过模型），所以模型此刻并不知道刚发生了什么 ——
  要么发完再问它一句，要么就只能让模型自己决定发不发。选前者：视频一定发得出去，
  锐评有没有是加分项。
- 提示词里**明确写了能力边界**（只看得到截图、听不到声音、帧间过程看不到），
  否则它一定会编背景音乐和连续剧情。
- 锐评生成失败**不影响视频已经发出这件事**，只写一行日志。

## 画面从哪来（本插件最关键的取舍）

**不用下载视频、不用 ffmpeg、不落盘。**

B站 为每个视频预生成了**逐帧缩略图拼图**（`videoshot` 接口）：默认 10×10 = 100 格，
格子横跨整个视频**均匀采样**，`index[i]` 就是第 i 格的**秒数**。

本机实测（2026-10-14）：

| 视频 | 时长 | 帧数 | 拼图张数 |
|---|---|---|---|
| BV1ZQWc6fE3L | 4.4 小时 | 1523 | 16 |
| BV1yEWw63E9Q | 11.9 分钟 | 124 | 2 |
| BV1iEpJ63E6z | 4.8 分钟 | 59 | 1 |
| BV11aaz6iEgN | 9.7 分钟 | 117 | 2 |
| BV1TKHQ62EZM | 11 分钟 | 119 | 2 |

5/5 全部拿到。把拼图交给 `deepseek-v4.1-flash`，它准确读出了
"第 1 格是室内女性人像，第 100 格是夜景烟花"，一次约 1000 token。

### 为什么不走"下载 + 抽帧"

那条路要 `node:fs`（落盘）和 `node:child_process`（调 ffmpeg）—— 这两样正是
插件加载器能力闸拦的东西。一旦导入，**整个插件会被判「触碰高危能力」拒绝加载**，
必须让用户在 `trustedPlugins` 里手工加信任才能用。

既然 B站 自己已经把帧准备好了，就没必要为同样的画面去付那个代价：
本插件**只用 fetch**，放进目录就能跑，不需要改任何信任配置。

> **可选升级**：如果以后需要"精确指定秒数"的画面（比如"看第 3 分钟发生了什么"），
> 再考虑引入 ffmpeg 裁剪路线。那时必须把 `bili-browse` 加进 `trustedPlugins`。

## 后台行为

- **每 45 分钟**检查一次，若手上没有备好的视频就去挑一个（纯抓取，不花 token）
- 启动后 12 秒补挑一个，不用等第一个间隔
- 挑的时候会**跳过已经看过的**（记最近 200 个），并按你设的时长/播放/点赞/时间区间过滤
- 挑好后**静静等着**，不主动发任何消息

**冷场递料什么时候才真的递出去**（全部满足才行）：

1. 这次唤醒是**主动机会**（`proactive`）—— 别人正聊天时插"我刚刷到个视频"很出戏
2. 不是 `atOnly` 模式
3. 不在静默时段（默认 1~7 点）
4. 今天分享次数没超上限（默认 6 次）
5. 距上次分享够久（默认 60 分钟）

递出去之后计数 +1，手上清空，下一轮再挑。

**触发词发送**只受 `triggerCooldownMin` 与 `triggerMaxPerDay` 约束，
不受静默时段与分享额度影响（理由见上方「两份账」一节）。

| `maxSharesPerDay` | `6` | 每天最多**冷场分享**几次 |
| `minMinutesBetweenShares` | `60` | 两次冷场分享最小间隔 |
| `quietHours` | `1,2,3,4,5,6,7` | 静默时段（留空 = 全天）。**只管冷场分享** |

| `triggerCooldownMin` | `20` | 两次触发发送最小间隔 |
| `triggerMaxPerDay` | `10` | 每天最多被触发几次（**独立于**分享额度） |
| `atOnly` | `false` | 仅 @ 模式 |
| `autoReview` | `true` | 发完自动补一句锐评 |
| `commentCount` | `5` | 带几条热门评论（0 = 不带） |
| `sheetCount` | `1` | 给几张画面拼图（每张 100 帧） |
| `sheetWidth` | `0` | 0 = 原图（4800×2700，最清楚） |
| `imageMode` | `url` | `url` 最省 / `base64` 内联 / `off` 只给文字 |
| `allowComment` | `false` | 允许在 B站 发评论 |
| `seenKeep` | `200` | 记住多少个看过的 |

### `imageMode` 怎么选

- **`url`（默认，推荐）**：把 B站 CDN 的图片地址交给模型。进请求体预算的只是
  那个 URL 字符串（约 90 字符），**图片多大都不占预算**，所以能直接用原图。
  本机实测网关能自己去抓这个地址。
- **`base64`**：本机抓下来内联。只在网关不支持外链图片时用 ——
  会**真的**把图片塞进请求体，所以会自动压到 1920 宽。
- **`off`**：只给标题/简介/评论，不看画面。

## 发评论（默认关闭，请先读这段）

`bili_comment` 会在 B站 上以**你的账号**留下一条**真实评论**：

- **删不掉，只能手动去删**
- 有**风控风险**（评论过快、内容被判违规都可能触发限制，见 `bili-api.js`
  的 `commentErrorText` 错误码表）
- 需要 `SESSDATA` + `bili_jct` 两项（浏览器登录 B站 后从 Cookie 里取）

所以默认关闭。要开：设置里打开「允许在 B站 下发评论」，填好两项登录态。
**读评论不需要登录**，只有发评论需要。

## 数据存在哪

- 看过的 BV 号、**冷场分享**计数 → `data/plugin-data/bili-browse/storage.json`
- **触发发送**计数（另一份账）→ 同一个文件里的 `triggerLog` 键
- 备好的视频只在**内存**里，重启即丢（下次启动会重新挑）

> ⚠️ **`api.storage` 是对象，不是函数。** 宿主 `createSkillApi` 里写的是
> `storage: makeSkillStorage(id)`，所以插件里要写 `api.storage.get(...)`。
> 曾经写成 `api.storage()` —— 那会抛 TypeError，而 `setup` 抛错会被加载器当成
> "加载失败"，表现为**整个插件静默不工作**（工具没注册、定时器没起），
> 日志里却只说"加载失败"，很难联想到是这一行。
> 现在的实现两种形状都兼容，并有回归断言盯着。

### 必须知道的坑

1. **能力闸是纯文本扫描，连注释都算。**
   `src/plugin-loader.js` 的 `CREDENTIAL_RE` 会匹配「凭据文件名」「主配置文件名」
   「进程环境变量对象」的字面写法。本文件所在的 `.js` 里**一个字都不能出现**
   （写成 `process` + `.env` 拼起来也算，因为是正则扫描源码文本）。
   要提它们就写在 `.md` 里 —— 扫描只看 `.js`/`.mjs`/`.cjs`。
   *（这个坑是实测踩出来的：`index.js` 最初那段"别写这些字样"的注释，
   本身就把插件拦下了。）*

2. **拼图 URL 是协议相对的**（`//bimp.hdslb.com/...`），不补 `https:` 模型取不到图。

3. **长视频别只取第一张拼图**：4.4 小时的视频有 16 张，第 1 张只覆盖开头 5%。
   这里按整段均匀抽，并把每张覆盖的时间范围写进提示词。

4. **注入一律追加到最后一条 user 消息末尾**：系统提示的前缀是缓存命脉，
   中间插入动态内容会让整段前缀缓存失效（`prompt.js` 的约定）。

5. **文字承诺必须与真实附带的内容一致**：`imageMode=off` 或模型不支持图片时，
   图片会被丢掉 —— 这时**不能再写"下面是 N 张拼图"**，否则模型会照着标题编画面。
   `buildBrief(entry, s, { withFrames })` 把"给不给图"的结论作为入参传进去，
   就是为了让文字和图片来自同一个决定。

6. **筛选里的"0"语义见上方专节** —— 写成 `值 > 0` 是最容易犯的错，
   `test-features.mjs` 里有专门的回归断言盯着它。

7. **`candidatePages()` 算出的页数必须真的传进 `searchVideos`。**
   这个 bug 真出现过：函数算了 `pages` 却没放进 options，翻页静默失效，
   而所有单元断言仍然全绿（它们只验 `searchVideos` 自己的翻页能力）。
   抓到它的是 `test-trigger-e2e.mjs` 里那句"实际请求了几次" ——
   **零件全绿不代表装配正确**，集成测试不能省。

## 附：顺手修掉的一个坏链（hot-trends 技能）

排查时发现 `plugins/hot-trend-tracker` 的提示词明确告诉模型：

> 「要聊最近的热搜、新梗时，先用 `hot_brief` 查本地知识库」

但**这个工具从来没被注册过** —— 插件只提供了 `knowledge.hot-trends` 能力，
负责"把能力变成工具"的技能那一半没有随包分发（`skills/` 下没有 `hot-trends` 目录）。
结果是模型被提示词引导去调一个不存在的工具，白烧一轮 token。

已补上缺失的 `skills/hot-trends/`（三个工具：`hot_brief` / `hot_status` / `hot_collect`），
它只做参数校验与结果转述，抓取与检索逻辑仍全部在插件里。
实测已能返回真实的 99 条热梗数据。

> 另外注意：`hot-trends` 的数据文件是 `data/hot-trends.json`（顶层 `data/`，
> 由 Electron 主进程用 `QQ_AGENT_DATA_DIR` 指定）。如果你在命令行里单独跑脚本验证，
> 记得先设这个环境变量 —— 否则 `src/config.js` 会按 `ROOT/../data` 解析到
> `resources/app/data/`（空的），看起来像"知识库是空的"。
